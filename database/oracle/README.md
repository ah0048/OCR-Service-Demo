# Oracle OCR test table

The standalone Python entry point is `backend/ocr-worker/oracle_worker.py`;
see [RUN_WORKER.md](RUN_WORKER.md) for connection setup, polling, multiple workers
and operation.

## Installation

For readable Unicode storage, stop writers and run `004_unicode_storage.sql`
after the earlier migrations. It converts CLIENT_ADDRESS/JOB_DESC to
NVARCHAR2(100)/NVARCHAR2(400) and both JSON columns to NCLOB, retaining previous
columns as *_OLD backups. DDL commits implicitly; inspect any partial failure
before resuming. Dependent views/procedures may need revalidation after renames.
The worker reads column metadata at startup and binds national character types
explicitly. New JSON is readable Arabic on NCLOB; older CLOB installations keep
using ASCII escapes safely until migrated. No database-wide charset change is
needed. Backups are retained until reviewed; old lost characters cannot be
recovered by type conversion alone. Existing escaped JSON remains valid but
escaped after migration; new results use readable text. Restart after migration.

For a table that already exists, stop workers and run
`002_add_extracted_fields.sql` in Toad as BRK_COD (F5). It adds MARITAL_STATUS and
RELIGION as VARCHAR2(100 BYTE), and EXTRACTED_JSON as CLOB only if missing.
Verify the final column types, then restart workers. No existing jobs are
reprocessed or backfilled automatically. Do not rerun the creation script.

Also run `003_add_ocr_details_json.sql` as BRK_COD (F5) before using the latest
worker. It adds OCR_DETAILS_JSON as CLOB only if missing; verify its final type.

Connect to Toad as **BRK_COD**, open `001_create_client_image_ocr_job.sql` in the
Editor and execute as a script (**F5**). All new objects belong to BRK_COD.
CREATE TABLE, CREATE SEQUENCE and CREATE TRIGGER privileges and space in the
schema's default tablespace are required. No explicit LOB or tablespace settings
are specified. The final queries must show a VALID insert trigger and no errors.

Before installation, check the connected account and effective privileges:

```sql
SELECT USER FROM DUAL;
SELECT PRIVILEGE FROM SESSION_PRIVS
WHERE PRIVILEGE IN ('CREATE TABLE', 'CREATE SEQUENCE', 'CREATE TRIGGER');
SELECT DEFAULT_TABLESPACE FROM USER_USERS;
SELECT TABLESPACE_NAME, BYTES, MAX_BYTES FROM USER_TS_QUOTAS;
```

If creation fails with ORA-01031 (insufficient privileges) or ORA-01950 (no
tablespace quota), a DBA must grant the missing access/quota. Connecting through
Toad does not bypass database permissions. An existing synonym with the same
name also needs review before installation; do not drop existing objects blindly.

The script creates new objects only, does not modify either existing table, and
has not been executed against Oracle. It is a one-time install. DDL commits
implicitly; inspect partially created objects before retrying a failed install.
If the previous draft was already installed, this script does not migrate it.

No synonym or self-grants are needed for BRK_COD's own job table. Existing source
images remain in CLIENTSOWNER.CLIENT_IMAGE_OCR, accessible through the previously
supplied SELECT grant/synonym. If a validation procedure owned by CLIENTSOWNER
will read/update this new BRK_COD table, arrange direct SELECT/UPDATE grants to
that owner separately; cross-schema procedure access is not automatic.

## Producer and source images

```sql
INSERT INTO BRK_COD.CLIENT_IMAGE_OCR_JOB (NIN_CODE)
VALUES (:nin_code);
COMMIT;
```

JOB_ID is generated by the sequence/insert trigger; STATUS defaults to PENDING.
One row represents a complete front/back pair. The producer inserts only when
both source images are ready. Repeated NIN_CODE values represent separate jobs.

Read CLIENT_IMAGE_OCR.DOC using NIN_COD and FILE_NUMBER 1 (front), 2 (back).
NIN_CODE is NUMBER(10), matching CLIENTS_OCR; source NIN_COD is VARCHAR2(20 BYTE).
Use an explicitly formatted text bind for source lookup. Confirm whether leading
zeros exist and how duplicate source rows are resolved; never pick an arbitrary
image or implicitly convert the whole source column to NUMBER.

## Extracted fields

| Inference field | Job column | Matching CLIENTS_OCR type |
| --- | --- | --- |
| fullName | CLIENT_NAME | VARCHAR2(100 BYTE) |
| gender | CLIENT_GENDER | VARCHAR2(1 BYTE) |
| nationalId | ID_NUMBER | VARCHAR2(20 BYTE) |
| birthDate | DATE_OF_BIRTH | DATE |
| address | CLIENT_ADDRESS | VARCHAR2(100 BYTE) |
| expiryDate | ID_EXPIRE_DATE | DATE |
| occupation | JOB_DESC | VARCHAR2(400 BYTE) in the job table |
| spouseName | HUSBAND_NAME | VARCHAR2(100 BYTE) |

The job table additionally stores `maritalStatus` in MARITAL_STATUS and `religion`
in RELIGION, each VARCHAR2(100 BYTE). These are raw Arabic labels, not numeric
codes; they have no matching columns in the supplied CLIENTS_OCR definition.

Gender mapping used by the Oracle writer:

- `ذكر` -> string `'1'` (male).
- `انثى` -> string `'2'` (female); accept `أنثى` as the same spelling variant.
- Missing/unrecognized values -> NULL, preserved in EXTRACTED_JSON for review.

The gender check accepts only '1', '2', or NULL; it validates codes but does not
translate text. The Python Oracle writer performs the mapping.

NIN_CODE is the client key, not the extracted national ID. Dates are bound as
date values. BYTE lengths match the supplied table exactly; check encoded
lengths for Arabic text and never silently truncate extracted fields.

Exception: the staging job table supports JOB_DESC length 400 (400 characters
after migration 004). CLIENT_ADDRESS likewise supports Unicode after migration.
CLIENTSOWNER.CLIENTS_OCR keeps its supplied VARCHAR2 byte limits, including
JOB_DESC 40 BYTE. Its validation procedure must handle conversion/length issues.

On older CLOB columns JSON uses ASCII Unicode escapes (ensure_ascii=True). The test
database uses AR8MSWIN1256: a read-only TO_CLOB round-trip replaced Arabic-Indic
digits with ASCII question marks. Escapes preserve every original Unicode value
inside CLOB without changing the database character set. JSON parsers restore
the original text; raw Toad JSON may display \\uXXXX sequences. This does not
change the charset of typed VARCHAR2 columns or repair already-corrupted rows.
After migration 004, NCLOB columns instead store readable Unicode JSON.

EXTRACTED_JSON retains the complete raw field dictionary, including gender,
marital status, religion and values that cannot fit destination columns. It
remains CLOB to hold JSON longer than Oracle 11g VARCHAR2 limits; only the
explicit LOB storage clauses were removed. Python validates/serializes the JSON.
OCR_OUTCOME preserves the detailed inference outcome, CONFIDENCE its heuristic
0..1 score, and ERROR_MESSAGE a short explanation (maximum 1000 characters).

OCR_DETAILS_JSON stores the complete `OcrOutput.details` report returned by the
inference adapter, separate from EXTRACTED_JSON. It retains per-side field
evidence, detector/recognition scores, ID agreement, review flags and confidence
breakdown when available. The existing adapter omits machine-local model/image/
crop paths; image bytes are not embedded. Error results retain their available
error details, or NULL if none were returned. Both JSON values and typed columns
are saved in the same result transaction. Historical rows are not backfilled.
This evidence can be joined through the job's NIN_CODE to source images for error
analysis and comparison with human-corrected labels; predictions are not labels.

## Simple test processing contract

1. A worker locks one PENDING row using SELECT FOR UPDATE SKIP LOCKED, changes
   it to UNDER_PROCESSING and sets STARTED_DATE. Commit before inference.
   This short atomic claim allows multiple workers to select different jobs.
2. Read both BLOBs and run paired OCR with the models already loaded.
3. Save fields/JSON/outcome/confidence and OCR_COMPLETED_DATE together with
   OCR_SUCCESS or OCR_FAIL. Guard the update by JOB_ID and UNDER_PROCESSING.
   Review flags alone do not cause OCR_FAIL: acceptance uses the overall 50%
   threshold, with terminal failures still rejected. Mapping warnings remain
   visible without overriding that score. See RUN_WORKER.md for the full policy.
4. Their validation procedure owns FINISHED. Human review is required even for
   OCR_SUCCESS; that status does not mean the data has been business-approved.

INSERT_DATE defaults to UTC; the worker must also write UTC to STARTED_DATE and
OCR_COMPLETED_DATE. No lease, heartbeat, retry, automatic reclaim, worker ownership
tracking or update trigger is included in this test version.

A caught exception can be saved as OCR_FAIL if the database is available. A
killed process, power failure or lost DB connection cannot guarantee that update;
the row can remain UNDER_PROCESSING. Once the old worker is definitely stopped,
mark its known interrupted job manually (use the specific JOB_ID):

```sql
UPDATE BRK_COD.CLIENT_IMAGE_OCR_JOB
SET STATUS = 'OCR_FAIL',
    OCR_OUTCOME = 'TechnicalError',
    ERROR_MESSAGE = 'Worker stopped before OCR completed',
    OCR_COMPLETED_DATE = CAST(SYS_EXTRACT_UTC(SYSTIMESTAMP) AS DATE)
WHERE JOB_ID = :job_id AND STATUS = 'UNDER_PROCESSING';
COMMIT;
```

Do not bulk-fail all processing rows or reset a live job to PENDING. Automatic
crash detection/recovery is deferred until the later testing phase.
